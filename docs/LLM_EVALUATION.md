# LLM 代码生成评估

## 实验设置

- 模型：GPT-5.6 Sol（Codex 桌面编程代理环境）；
- 输入：一份完整需求提示词，包含技术约束、P0/P1、架构、测试、文档与验收标准；
- 工作方式：代理读取空仓库，直接创建源码，分阶段调用 CMake/MSVC、CTest、真实 OpenGL 程序与帧缓冲截图；
- 人工/工具检查：编译诊断、测试退出码、OpenGL 标识、截图视觉检查、Git diff/文本扫描；
- 对照实验：未进行其他模型对比，因此本文不声称模型优劣排名。

## 生成过程中的实际问题

1. 初始 CMake 假定 GLAD 2 的 `glad_add_library` 会自动导入。配置失败后检查依赖源码，改为显式包含 `GladConfig.cmake`。
2. 随后 GLAD 生成步骤报 `No module named glad`。改为配置期检测 Python 模块，并从固定的已下载源码安装生成器。
3. 首次程序运行成功创建 OpenGL 3.3 上下文，但着色器打开失败。原因是 Windows 中文目录和窄字符 `ifstream`，改用 `filesystem::u8path`。
4. 第一张内部截图几乎全黑。程序没有崩溃，真正原因是相机位于实体巷帮外侧。把视角移入巷道，并为顶视提供剖面表现。
5. 第二张截图被通风管和默认日志窗遮挡。继续调整相机横向位置、默认 UI 展开状态和灯具发光强度，第三张才达到可演示构图。

这些问题说明“代码可编译”远低于“图形系统可用”。LLM 需要真实运行反馈，尤其是窗口、资源路径、视角和画面层次。

## LLM 表现较好的部分

- 从长需求提取模块边界和状态枚举；
- 快速生成可复用 Mesh、Shader RAII 和 CMake 目标；
- 把设备联动转成可测试的确定性逻辑；
- 同时维护代码、测试、构建脚本和解释文档；
- 根据编译器错误和截图反馈做局部修复；
- 生成覆盖非法转换、安全联锁和边界值的逻辑测试。

## 需要重点人工检查的部分

- OpenGL 上下文和驱动兼容性；
- 矩阵顺序、法线矩阵、剔除方向和透明顺序；
- 相机是否在几何体内部/外部、近远裁剪和视野构图；
- 急停、复位、故障清除的安全语义；
- CMake 第三方依赖真实版本和离线行为；
- UI 是否真的影响设备，而非只改文本；
- “工业真实性”措辞，避免把教学演示误称生产系统。

## 适合与不适合完全交给 LLM 的任务

适合：课程级程序化几何、状态机样板、RAII 包装、逻辑测试、说明文档、构建错误定位。

不适合无人工复核：煤矿工艺参数、安全认证、真实 PLC/传感器控制、性能和硬件兼容性结论、工业级设备尺寸、视觉审美最终把关。当前项目明确不承担这些用途。

## 结论

本次单模型实验表明，详细提示词可帮助模型生成结构完整的图形课程项目，但可靠交付依赖“生成 → 构建 → 测试 → 运行 → 截图检查 → 修复”的闭环。若跳过后四步，至少 GLAD 集成、中文路径和默认相机构图三个缺陷都会被错误地当作完成。
